# Executable proof verdicts — 2026-07-13

All new runtime proofs load `main.js` in a VM and satisfy `evalFile` by reading and parsing the matching committed `ext*.js` file. `tools/proofs/platform.js` derives its storage allowlist and seed from `data.json` at runtime, builds I/O bags from `manifest.json`, logs every storage call, and supports per-call/per-key/predicate throws. No production logic is mirrored in a proof.

Run the complete set with:

```bash
bash tools/proofs/run-all.sh
```

The runner treats a matching verdict/exit pair as a valid proof result: PROVEN/1, REFUTED/0, INCONCLUSIVE/2.

## Corrections to the first audit

F1 was labelled VERIFIED by assuming a firmware rule that was not established by a committed log, pulled save file, or platform contract. That was overconfident. The source asymmetry and both failure consequences are now executable facts, but the headline remains INCONCLUSIVE until `data.jsn` selects a firmware policy. The generic watch-log line `ERR APPLICATION : localStorage: reading b:/zapp/storage/climbl01/data.jsn` is not key-specific evidence and must not be promoted into it.

F8 was wrong at the severity-defining step. I treated tracked release-looking archives as the supported deploy payload and described README as directing their deployment. The actual `bledeploy.sh` uses committed archive names only to derive `appID`, builds source into `/tmp/bledeploy.*`, and passes that new file to `deploy.py`; `deploy.py` transmits exactly the caller-supplied bytes. A person can manually point the low-level tool at a stale archive, but no checked workflow does so. The archives are stale repo hygiene (P3), not evidence that the normal deploy ships stale code (P0).

F12 remains speculative because forcing a lifecycle callback in Node is evidence about app behavior, not firmware reachability. F13 and F14 were outside the requested script list and remain unproven here; they should not receive fixes merely because their static arguments look plausible.

## Recommended next-round order

1. Run the F1 and F12 hardware experiments first. If F1 selects either strict policy, declare all ten `pS` keys before using cross-system project tests; this is the dependency for validating F2 across arbitrary A→B→A systems.
2. Fix F3 (accepted) and F2 together after the storage schema decision. They are deterministic project-history destruction on normal user actions and need one cross-system/two-session regression contract.
3. Fix F4, then F5. Migration must establish a trustworthy authoritative shard before END can write; after that, write the authoritative shard before the derived mirror and rerun failure injection at every write boundary.
4. Fix F6 and F7 as one parse-safety pass. F6 removes the normal `ext14` press parse and the `ext21` press retry; F7 still needs bounded `f3` and `ext25`. If counters need resident bytes, prove F13's candidates before using that cleanup as the budget source.
5. Fix F11, then choose an honest F9 behavior before implementing broader folded editing. Both affect post-route correction, but F11 is a compact persisted invariant while F9 needs a product decision about immutable folded history.
6. Decide whether to implement or remove F10's nine dead advertised records. Totals and active mirrors are live, so schema removal is lower-risk than inventing history semantics late.
7. Clean stale archives as P3 and correct persistence documentation only after runtime behavior stabilizes. F13/F14 need their own proof gate before changes.
