## Environment

- Watch: Suunto Vertical 2, firmware **2.53.42** (HW 1424B3)
- Reproduced across many sessions over several days; full device logs available
- **Update (2026-07-10): this is not specific to my own app.** I have now reproduced the freeze using **only Suunto's own SuuntoPlus apps**, with my app uninstalled (Evidence 6) — including your own climbing app `zzclimen`. I have also corrected two claims in the original version of this post that turned out to be wrong, and added a controlled four-probe experiment that isolates what actually leaks (Evidence 8).

## Symptom

The trigger is **repeatedly toggling one app off and on inside the SuuntoPlus enable/disable menu, without leaving that menu**. After enough toggles the watch UI locks up.

**It has never once recovered on its own.** Every time, I had to plug in the USB cable or force a restart. (An earlier version of this post claimed a ~45 s self-heal — that was my mistake, see Evidence 2.)

How many toggles it takes depends on **how much the app's `main.js` keeps in its module scope** — not on its byte size (Evidence 8 isolates this): my own app (~40 module-level functions) dies on the **second** in-menu re-enable; Suunto's own **Gear Tracker** and **Suunto Climb** take about ten; a probe app with an almost-empty module scope survives 50+ regardless of templates or storage.

The key observation: **leaving the enable/disable menu makes the problem go away.** Leaving the menu is exactly what triggers the `JS discard` (Evidence 1), which frees the leaked contexts — so a toggle followed by a menu exit never fails; only repeated *in-menu* toggling does.

## Evidence 2 — the freeze is an allocation storm during `Load script`, before any app code runs

Cleanest trace, 2026-07-09, my own app (`main.js` 7.5 KB minified). An activity is recording, three apps enabled, nothing else touched:

```
15:20:55 : EVT APPLICATION : Zapp climbl01:Disable        <- single-app disable #1, no discard
15:20:57 : EVT APPLICATION : Zapp climbl01:Load script
15:20:57 : EVT APPLICATION : Zapp climbl01:Enable         <- clean
15:20:59 : EVT APPLICATION : Zapp climbl01:Disable        <- single-app disable #2, no discard
15:21:00 : EVT APPLICATION : Zapp climbl01:Load script
15:21:01 : ERR APPLICATION : Zapp:relMemCb (exec:zapp)
15:21:01 : EVT APPLICATION : Zapp zzwethen:Disable
15:21:01 : ERR APPLICATION : Zapp 3:RelMem->unload
15:21:01 : EVT APPLICATION : Zapp zzmoveen:Disable
15:21:01 : ERR APPLICATION : Zapp 3:RelMem->unload
15:21:01 : ERR APPLICATION : Zapp:RelMem->None avail
15:21:01 : ERR DUKTAPE     : JSalloc:2636                 (x11, all within this one second)
15:21:01 : ERR DUKTAPE     : Compiling js failed: Error: 1
15:21:01 : WRN APPLICATION : Script load:other
15:21:01 : EVT APPLICATION : Zapp climbl01:Disable        <- firmware gives up, disables the app
15:21:01 : ERR APPLICATION : Zapp ?: Exec. event 1024 failed (zapp disabled)
```

Three things about this trace:

- The loader wanted a **2636 B contiguous** block and never got one — not even after the firmware force-unloaded the two *other*, innocent zapps (`RelMem->unload`). `None avail` kept coming.
- There is **no `JS discard disable zapps`** between the two disables.
- **No cable, and no recovery.** `VBUS state is ON` appears nowhere in this file, and there is **not one further `Zapp climbl01:Load script`** until the watch is restarted 27 minutes later.

An older run of the same app (7.8 KB) has the same shape with a much larger burst — **58** failed allocations in one second (`JSalloc:1964` ×44, `:2392` ×11, `:2095` ×3) → `Compiling js failed: Error: 1`.

In that older log the app does come back 41 s later. **I originally reported this as self-healing. That was wrong.** Correlating the charger against it:

```
22:08:18 : ERR DUKTAPE     : Compiling js failed: Error: 1
22:08:18 : EVT APPLICATION : Zapp climbl01:Disable
22:08:21 : EVT PMIC        : VBUS state is ON      <- I plugged the cable in, 3 s after the fatal
22:08:22 : EVT PMIC        : VBUS state is OFF
22:09:02 : EVT APPLICATION : Zapp climbl01:Load script
22:09:02 : EVT APPLICATION : Zapp climbl01:Enable  <- 41 s AFTER the cable pulse
```

A cable-rescued watch logs a plain `Enable`, indistinguishable from a clean one. Anyone reading these logs should correlate every `Enable` against `VBUS state is`.

## Evidence 3 — every toggle whose disable logged a `JS discard` re-enabled cleanly

In that same session, the three toggle cycles right before (disables at 22:06:10, 22:07:32, 22:07:58) each show `JS discard disable zapps` at the disable and re-enabled without a single allocation failure. The one cycle whose disable logged **no** discard (22:08:15) is exactly the one that stormed.

## Evidence 4 — how many toggles it takes: the ladder across all apps

All sizes below are the `main.js` as actually shipped inside the `.fea` (minified), measured by unzipping the bundles — the Suunto ones straight off the watch. The second column counts the module-level function expressions the compiled dispatcher closes over; Evidence 8 shows this, not the byte size, is what matters.

| app | `main.js` | module fns | in-menu single-app re-enables |
|---|---|---|---|
| Weather (`zzwethen`) | 454 B | 0 | 15 at ~1 s spacing, never failed (my control) |
| Indoor Climbing (`zzinclen`) | 781 B | 0 | ~25, all clean |
| Movement (`zzmoveen`) | 1 261 B | 3 | never observed to fail |
| ZoneSense (`zzaeroen`) | 2 166 B | 3 | ~30, all clean |
| **Gear Tracker (`zzgearen`)** | 2 349 B | **14** | **~10 → heap at 99.3 % → freeze** |
| **Suunto Climb (`zzclimen`)** | 2 941 B | **10** | **~10 → `JsTotMem` warning at #7 → freeze** (fresh reboot, alone) |
| Suunto Wing 2 (`zzsuunen`) | 3 449 B | 20 | not comparable — headphone device driver, each re-enable runs a hardware search |
| my app — stub build | 266 B | — | 19 consecutive clean at ~1/s |
| my app — stripped build | 4 060 B | — | 4 clean, 5th stuck (see below) |
| my app — production | 7 496 B | ~40 | 1 clean, **2nd storms** (Evidence 2) |

Note the pair that kills the naive size story: ZoneSense (2 166 B, 3 module functions) survives ~30, Gear Tracker (2 349 B, 14 module functions) dies at ~10 — 183 bytes apart, 3× apart in toggles. And `zzclimen` is your own climbing app: it freezes about as fast as Gear Tracker despite carrying no settings and a 2-byte store.

One honest caveat: the Indoor Climbing and ZoneSense runs happened in the *same* session, before the first Gear Tracker one, so those counts are not independent — but Gear Tracker and Suunto Climb were each retested **alone, from a fresh reboot**, and reproduced at ~10.

I first isolated `main.js` as the carrier with three builds of the *same* app — identical manifest, identical data store, identical templates and ext files, **only `main.js` changed**. The 266 B stub ships all of them unchanged and never fails, which rules out the manifest, settings/variables, data store and templates as carriers. Evidence 8 then narrows it further to what `main.js` *retains*.

## Evidence 6 — it reproduces with Suunto's own apps, and then there is no error line at all

**2026-07-10. My app was uninstalled — only Suunto's own SuuntoPlus apps were on the watch.** Activity recording; toggling one app at a time in the enable/disable menu, roughly once per second:

```
08:09:27-08:09:54 : Zapp zzinclen (Indoor Climbing) : ~25x Disable -> Load script -> Enable, all clean
08:09:57-08:10:17 : Zapp zzaeroen (ZoneSense)       : ~30x, all clean
08:10:18          : EVT APPLICATION : Zapp zzgearen:Enable      (Gear Tracker)
08:10:19          : WRN UI_FRAMEWORK : JsTotMem 132188/133120   <- JS heap 99.3 % full
08:10:21          : last zapp event of any kind; UI frozen
08:26:20          : TRC APPLICATION : Start wuiapp 2.53.42 in mode 5   <- I had to restart it
```

After that restart, Gear Tracker **on its own** reaches the same point:

```
08:44:33 : EVT APPLICATION : Zapp zzgearen:Enable, then ~10 in-menu re-enables at ~1/s
08:44:45 : WRN UI_FRAMEWORK : JsTotMem 132180/133120

```

There is **no `JSalloc`, no `relMemCb`, no `Compiling js failed`** anywhere in this window. With a small app the compiler still finds its contiguous block; the shared heap simply fills up. Same cause, different way to die — and in this variant the firmware log contains **nothing that looks like an error**, just that one `JsTotMem` warning.

The ceiling is visible in that line: **133 120 bytes** of JS heap, shared by all enabled SuuntoPlus apps.

## Evidence 7 — the leaked contexts also break the *next* end-of-session save

The un-discarded contexts don't only block a re-enable; they starve the next ~2 KB contiguous allocation the app makes. After a few in-menu re-enables during an activity, **ending** the exercise storms on the same allocation class — the failure fires at my end-of-session `evalFile`, before any of that code runs:

```
17:08:24 : EVT UI_FRAMEWORK : evalFile: b:/zapp/climbl01.fea/ext11.js from ui
17:08:24 : ERR APPLICATION  : Zapp:relMemCb (exec:zapp)
17:08:24 : ERR APPLICATION  : Zapp 3:RelMem->unload      (Weather + Movement force-unloaded)
17:08:24 : ERR APPLICATION  : Zapp:RelMem->None avail
17:08:24 : ERR DUKTAPE      : JSalloc:2137               (x11)
17:08:30 : EVT PMIC         : VBUS state is ON           (cable again)
```

It is dose-dependent: earlier in the same session, with fewer leaked contexts, the same end produced only three failures (`JSalloc:2117` ×3) and carried on. So the missing discard has a second, downstream cost: an allocation that is perfectly reliable on a freshly discarded heap fails once un-discarded contexts have piled up.

## Evidence 8 — controlled probes: the leaked unit is the app's instantiated module scope

To separate the candidate causes I built four minimal probe apps and toggled each one **alone, from a fresh reboot**, in the enable/disable menu (~1/s, staying in the menu, no cable):

| probe | `main.js` | module-level functions | templates | localStorage | result |
|---|---|---|---|---|---|
| P0 (baseline) | 134 B | 1 | 1, bare | none | **56 re-enables, clean** |
| P2 (template axis) | 134 B — byte-identical to P0 | 1 | **4, each carrying 775 B of `<onLoad>` JS** (copied verbatim from `zzclimen`) | none | **49, clean** |
| P3 (storage axis) | 233 B | 1 | 1, bare | **2× `getObject` on a 1 015 B store at every re-enable** | **50, clean** |
| P1 (module-scope axis) | 1 446 B | **20** | 1, bare — identical to P0 | none | **froze at ~10 — reproduced twice** |

P0 and P1 differ in exactly one property: the number of module-level function expressions the lifecycle dispatcher closes over (1 vs 20). Templates — even four of them full of JS (P2) — and localStorage traffic (P3) are acquitted.

So what a single-app disable leaks is the app's **instantiated module scope**: the compiled function objects plus their captured environment. Each no-discard re-enable stacks another full copy onto the shared 133 120 B heap, and the size of that scope sets how many toggles fit before the watch dies.

One more detail for the firmware team: P1's freeze produced **no log line whatsoever** — no `JsTotMem`, no `JSalloc`, no error. In both runs the final `Load script` → `Enable` pair looks perfectly normal in the log; the UI simply never responded again (the charger pulse 10 s later is me rescuing it, not a recovery).

The four probes are each under 20 lines of source; happy to share them as `.fea` or source.

## Analysis (proven vs. inferred)

Proven from the logs:

- `JS discard` is only ever logged on the all-zapps-disable path (and on exercise stop), never after a single-app disable.
- With a large app the fatal event is the script loader failing to allocate a ~2 KB contiguous block during `Load script` — while compiling, before any of the app's own code executes.
- Force-unloading the other zapps mid-storm does not resolve it (`RelMem->None avail` continues).
- With a small app there is no allocation failure at all; the only trace is `JsTotMem 132188/133120`, and then the UI is gone.
- **The watch never recovers on its own.** Every apparent recovery in my logs is preceded by a `VBUS state is ON` (charger) or a restart.
- The carrier is `main.js`: identical manifest, data store and templates with a 266 B `main.js` never fail.
- Within `main.js`, the leaked unit is the **instantiated module scope** (Evidence 8): 20 module-level functions → freeze at ~10; 1 module-level function, byte-identical lifecycle → 56+ clean; templates and localStorage traffic separately ruled out.

Inferred (my best explanation, happy to be corrected):

- Without the discard, each single-app disable leaves that app's instantiated module scope — function objects plus environment — in the shared Duktape heap. They accumulate. Which way you die depends on which resource runs out first: a big app's compile buffer cannot be *placed* (fragmentation → `JSalloc`), while many small leaks simply *fill* the heap (→ `JsTotMem`, or no line at all). After exercise stop — where the discard does run — the same app always re-enables cleanly.

## Minimal reproduction (no third-party code needed)

1. Start any activity with a couple of SuuntoPlus apps enabled.
2. Options → SuuntoPlus → disable **Gear Tracker**, then re-enable it, **without leaving the menu**.
3. Repeat, about once per second.
4. Around the tenth in-menu re-enable the UI locks up, and the log shows `WRN UI_FRAMEWORK : JsTotMem 1321xx/133120`. It will not come back; cable or restart.

Bigger apps get there sooner — my own 7.5 KB app dies on the *second* in-menu re-enable, with the `JSalloc` storm of Evidence 2.

The only workaround I have found: **leave the enable/disable menu between toggles.** That triggers the discard, and it never fails.

## Questions

1. Is skipping the `JS discard` on a single-zapp disable intentional, or a bug?
2. If intentional: could the firmware run the discard (or a heap compaction) on a single-zapp disable too? That would remove this freeze entirely.
3. Is there official guidance on the ~133 KB shared JS heap budget, and on fragmentation behaviour when several SuuntoPlus apps are enabled? The apizone docs don't cover memory.
4. In the `JsTotMem` variant the firmware logs no error at all before the UI dies — and in the probe-P1 variant (Evidence 8) **nothing at all** is logged: the final `Load script`/`Enable` pair looks perfectly healthy. Would it be possible to surface an allocation/heap failure there?
5. I have full device logs of all of the above and am happy to share them, or to file this through another channel if preferred.
